# engine-flag-discovery Specification

## Purpose

Defines how the `llama-atomic` and `llama-cuda` engine Dockerfiles bake a self-describing `/etc/llama-engine/flags.toml` into each image at build time, by capturing `llama-server --help` in the builder stage and parsing it with a new `extract_flags.py`. The baked schema is the contract consumed by `engine-flag-schema` at runtime.

## Requirements

### Requirement: REQ-001 Build-Time `--help` Capture in the Builder Stage

Both `llama-atomic/Dockerfile` and `llama-cuda/Dockerfile` MUST capture `llama-server --help` in the builder stage and COPY the resulting `/etc/llama-engine/flags.toml` into the runtime image. The capture step MUST export `LD_LIBRARY_PATH=/usr/local/cuda/lib64/stubs` for that step (the stub already exists at `/usr/local/cuda/lib64/stubs/libcuda.so.1` via the existing `ln -sf` at atomic Dockerfile:7 / cuda Dockerfile:8) and redirect stderr to `/dev/null` to silence the expected `ggml_cuda_init: failed to initialize CUDA: CUDA driver is a stub library` warning.

#### Scenario: atomic builder captures --help

- GIVEN the `llama-atomic` builder stage has compiled `llama-server` (atomic Dockerfile:27-29)
- WHEN the capture step runs with `LD_LIBRARY_PATH=/usr/local/cuda/lib64/stubs` and stderr redirected to `/dev/null`
- THEN `flags.toml` is generated by `extract_flags.py` AND the runtime image contains `/etc/llama-engine/flags.toml`

#### Scenario: cuda builder captures --help

- GIVEN the `llama-cuda` builder stage has compiled `llama-server` (cuda Dockerfile:24-26)
- WHEN the same capture step runs in the cuda builder
- THEN the cuda runtime image contains `/etc/llama-engine/flags.toml`

### Requirement: REQ-002 Loud Failure on Unrecognized Help Format

`extract_flags.py` MUST exit non-zero when the `--help` text does not match the expected per-line flag format. The build MUST fail rather than silently baking a partial schema that would under-validate at runtime.

#### Scenario: Parser rejects unknown format

- GIVEN `llama-server --help` output whose flag lines do not match the parser's expected `-short, --long ARG` columnar shape
- WHEN `extract_flags.py` runs during the image build
- THEN the script exits non-zero AND the image build fails

### Requirement: REQ-003 Reproducible-Build Knobs Unchanged

The change MUST NOT alter `SOURCE_REF`, `GGML_CUDA=ON`, `CMAKE_CUDA_ARCHITECTURES=86`, or `GGML_NATIVE=OFF` in either Dockerfile (atomic Dockerfile:12,27; cuda Dockerfile:12,24).

#### Scenario: Pinned knobs preserved

- GIVEN the change is applied to both Dockerfiles
- WHEN the diff is reviewed
- THEN `SOURCE_REF`, `GGML_CUDA`, `CMAKE_CUDA_ARCHITECTURES`, and `GGML_NATIVE` values are byte-identical to the pre-change Dockerfiles

## Non-Goals

- `llama-tom/Dockerfile` — uses a prebuilt binary with no builder stage for `--help`; deferred to a follow-up change.
- Generating `flags.toml` on the NUC and `COPY`ing it in (fallback plan B from the proposal) — not needed; stub verification confirmed plan A works (see Resolved Risks).
- Parsing the 6 base CLI flags into the schema — they stay hard-coded in `ai-wrapper/main.py`.

## Resolved Risks

- **`llama-server --help` fails in builder** (proposal risk #1, HIGH) — **RESOLVED**. Engram observation `discovery/llama-server-stub-help` confirms `--help` runs successfully when the builder's existing stub is exposed via `LD_LIBRARY_PATH`; argparse exits before any functional CUDA call, and the `cuInit()` warning on stderr does not abort. The "No build-time smoke check" comment at `llama-atomic/Dockerfile:39-40` is superseded by this verification and should be updated by the implementation.
